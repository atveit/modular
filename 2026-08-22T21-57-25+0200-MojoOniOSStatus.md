# Mojo on iOS status

Snapshot time: 2026-08-22 (updated after the bounded core-seed and Bzlmod-ladder checkpoints)

## Summary

The runtime-free “Mojo object → Apple archive → C ABI → Simulator app” path is
working and reproducible. This is beyond a proof of concept, but it is not yet
production-quality Mojo iOS support.

Latest pushed commit at snapshot time: `cf46b13f5e` (`[Mojo] Advance bounded
iOS runtime and graph gates`). The CcInfo provider, two-slice Bazel archive
seam, isolated Apple-rule archive consumer, pinned-compiler smoke default, emitted-Mojo global probe, bounded
Error/no-stack-trace probe, and composite core-seed probe are tracked. The
disposable Bzlmod ladder is also tracked; it deliberately leaves the root
module and lockfile unchanged.
Per-agent evidence logs remain local and intentionally untracked.

## Demonstrated evidence

- Simulator archive: `IOSSIMULATOR`, iOS 17, `mojo_add`, and
  `mojo_hello_utf8`.
- Device archive: `IOS`, iOS 17, using the conservative `apple-a7` baseline.
- The smoke harness prefers the repository-pinned compiler.
- A command-line-built and signed Simulator app launches successfully.
- An isolated `rules_apple`/`rules_swift` workspace consumes the Mojo archive
  through `cc_import` and produces an iOS 17 Simulator IPA.
- The Bazel rule returns `CcInfo`, so a future same-graph Apple target can use
  the generated header/archive without a `bazel-bin` path.
- The experimental `GlobalsIOS.cpp` candidate links with a real Mojo `_Global`
  probe and passes `MOJO_COMPILERRT_GLOBALS_MOJO_PROBE_PASS` on the Simulator.
- A separate `StackTraceIOS.cpp` candidate links an emitted Mojo Error probe and
  passes `MOJO_COMPILERRT_ERROR_PROBE_PASS`, explicitly with stack traces
  unavailable.
- A composite SDK-native core-seed archive links both emitted probes and
  passes `MOJO_COMPILERRT_CORE_SEED_PROBE_PASS`; this remains a narrow
  non-AsyncRT candidate, not the production runtime.
- KGEN and iOS-target tests pass.
- Device artifact preparation passes without signing or installation.

## Main blockers

1. Root Bazel integration needs a dependency decision. The existing
   `rules_apple`/`rules_swift` versions are incompatible with Bazel 9.2; the
   tested compatible pair requires a protobuf 34 upgrade.
   A same-graph control advances past versionless `rules_mojo` and Jammy
   sysroots only with disposable local overrides, then stops because the
   consumed `modular` module cannot see its `@rules_mypy` development-dependency
   repository. A disposable protobuf-34 trial showed that the old development-
   dependency patch can be removed or ported for focused graph/KGEN checks, but
   the Apple transition still fails under Bazel 10; this is a dependency-owner
   migration rather than an iOS-only fix.
2. The Bazel archive action discovers Xcode SDK tools through `xcrun` and runs
   locally/non-sandboxed. It is real archive evidence, but not yet a hermetic
   Apple Bazel toolchain.
3. The full iOS-safe Mojo runtime is incomplete. Allocation, String lifetime,
   named-global teardown, and a no-stack-trace Error construction path have
   narrow Simulator evidence; `initialize_runtime()` still reaches AsyncRT
   CPU-device, thread-pool, TCMalloc, and global-runtime dependencies.
4. Physical-device signing, installation, and visible “Hello from Mojo” remain
   unverified.
5. Performance claims, Swift comparisons, broad Apple framework coverage, Core
   ML/ANE validation, Mojo-generated Metal kernels, CI, and upstream-quality
   packaging remain ahead.

## Estimated timeline

Assuming focused engineering time and no major compiler/runtime redesign:

- Root CcInfo provider seam: complete; same-graph Apple consumption still
  depends on the root rules/toolchain decision.
- Root Apple-rule dependency/toolchain decision and canonical Bazel app:
  approximately 1–2 weeks, depending on protobuf-upgrade approval.
- Physical iPhone “Hello from Mojo”: approximately 1–3 days once a
  development-signed device is available.
- Usable static runtime plus allocation/String/error/core-stdlib subset:
  approximately 3–8 weeks; allocator/String, globals, and the no-stack-trace
  Error path are now bounded probes, while this remains the highest-risk phase.
- Initial device benchmarks and Swift comparison: approximately 2–4 weeks after
  runtime/device support.
- Broader framework adapters and Core ML packaging: approximately 1–3 months
  incrementally.
- Mojo-generated Metal on iOS: likely several additional months after iOS AIR
  lowering is implemented.
- Production-quality/upstreamable support: realistically 3–6+ months, with
  complete iOS/Swift framework coverage continuing as a staged effort.
