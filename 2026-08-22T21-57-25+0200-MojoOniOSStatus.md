# Mojo on iOS status

Snapshot time: 2026-08-23 (updated after the N9 canonical app checkpoint)

## Summary

The runtime-free “Mojo object → Apple archive → C ABI → Simulator app” path is
working and reproducible. This is beyond a proof of concept, but it is not yet
production-quality Mojo iOS support.

Upstream integration baseline: `6996a6343d` (`[Mojo] Update static-library
test for def syntax`), following merge commit `6a4d2613c6`. The CcInfo provider, two-slice
Bazel archive seam,
isolated Apple-rule archive consumer, pinned-compiler smoke default,
emitted-Mojo global probe, bounded Error/no-stack-trace probe, composite
core-seed probe, target-correct Bazel core-seed archives, and screenshot-backed
SwiftUI host validation are tracked. The
disposable Bzlmod ladder is also tracked; it deliberately leaves the root
module and lockfile unchanged.
Per-agent evidence logs remain local and intentionally untracked.

## Demonstrated evidence

- Simulator archive: `IOSSIMULATOR`, iOS 17, `mojo_add`, and
  `mojo_hello_utf8`.
- Device archive: `IOS`, iOS 17, using the conservative `apple-a7` baseline.
- The smoke harness prefers the repository-pinned compiler.
- A command-line-built and signed Simulator app launches successfully.
- An isolated `rules_apple`/`rules_swift` workspace consumes the Mojo archive
  through `cc_import` and produces an iOS 17 Simulator IPA.
- The Bazel rule returns `CcInfo`, so a future same-graph Apple target can use
  the generated header/archive without a `bazel-bin` path.
- The experimental `GlobalsIOS.cpp` candidate links with a real Mojo `_Global`
  probe and passes `MOJO_COMPILERRT_GLOBALS_MOJO_PROBE_PASS` on the Simulator.
- A separate `StackTraceIOS.cpp` candidate links an emitted Mojo Error probe and
  passes `MOJO_COMPILERRT_ERROR_PROBE_PASS`, explicitly with stack traces
  unavailable.
- A composite SDK-native core-seed archive links both emitted probes and
  passes `MOJO_COMPILERRT_CORE_SEED_PROBE_PASS`; this remains a narrow
  non-AsyncRT candidate, not the production runtime.
- Separate Bazel targets now SDK-compile that core seed for Simulator and
  device, validate all archive members and ten runtime exports, and feed the
  artifacts back into the emitted-Mojo link/run harness. These local Xcode
  actions are target-correct but not yet hermetic root Apple-toolchain actions.
- The same archive now includes a libc-only formatted-print shim. A real Mojo
  stdlib export roundtrips a process-local environment value and performs
  `open`/write/read at an app-owned `TMPDIR` path in Simulator, while its device
  variant passes artifact-only link and metadata gates. This is narrow
  environment/sandbox-file evidence, not general filesystem or AsyncRT support.
- N1 now records exact undefined-symbol allow-lists for allocating String,
  Error, `_Global`, and environment/file objects on both iOS triples. The gate
  fails on any new symbol or `KGEN_CompilerRT_AsyncRT_*` dependency.
- N2 replaces the ambiguous host-runtime naming with an explicit
  `CompilerRTIOSBootstrapHost` diagnostic and `CompilerRTIOSCoreSources`
  serial contract. Canonical device/Simulator archives reject AsyncRT, Python,
  JIT, Tracy, and TCMalloc symbol families; compatibility aliases remain.
- N3 serializes global creation, lookup, insertion, and teardown with one
  recursive mutex. The Simulator gate passes 64 lifecycle rounds with eight
  concurrent native threads and exact named/indexed create/destroy counts.
  This is race/lifetime correctness evidence, not a lock-free or contention
  performance claim; host TSan was unavailable because its runtime exited
  before the test body.
- N4 runs real Mojo formatting/output, `List`, monotonic clock, errno/Error,
  path, restricted environment, nested sandbox-directory, and ordinary-file
  operations in Simulator; the same object links for device with `IOS` iOS 17
  metadata. All 38 top-level stdlib packages import for both triples, while
  process spawning now fails with an explicit iOS compile-time diagnostic.
- N5 runs 10,000 caller-buffer, opaque-handle create/read/destroy,
  Error-to-status, scalar, and allocating String calls in Simulator with a
  clean exit. Device and Simulator images are dead stripped, an unused Mojo
  export is absent, and force-loading two copies of the serial runtime fails
  explicitly. This is not a sanitizer-backed no-leak/no-race claim.
- N6 promotes the Bazel-10 Apple dependency graph, and N7 registers separate
  iPhoneOS and iPhoneSimulator SDK repositories plus exact arm64 iOS 17 C++
  toolchains. The checked-in one-file gate builds `IOS` and `IOSSIMULATOR`
  Mach-O binaries, and its action inspection finds the exact SDK repository
  and triple with no action-time `xcrun`. Target sanitizers remain unsupported
  rather than reusing macOS sanitizer runtimes.
- N8 builds deterministic runtime-free Mojo and bounded serial CompilerRT
  archives through the registered target toolchains for both Apple mobile
  platforms. Every member reports `IOS` or `IOSSIMULATOR` with iOS 17, the
  archives return `CcInfo`, and a same-graph C consumer links for both targets.
  Action inspection finds declared SDK inputs and no action-time `xcrun`,
  `local`, or `no-sandbox` escape. Because Xcode is a local host dependency,
  this is sandboxed/reproducible local-Xcode evidence, not remote execution.
- N9 builds the canonical SwiftUI app from the same Bazel graph as the Mojo
  archive and bounded serial core. XCTest executes both C exports; XCUITest
  asserts the exact visible greeting and calculation; the gate then installs,
  launches, and captures the app on an arm64 iPhone Simulator. The final image
  exports both Mojo functions and contains one serial-core initializer. This
  is not `std.runtime.initialize_runtime()`, AsyncRT, or physical-device proof.
  The final Swift app link uses Xcode's Apple linker through the repository
  wrapper, so it is local-Xcode reproducible rather than remote-hermetic.
- N10 combines exactly one Mojo archive and one bounded serial-core archive for
  each platform, packages the distinct variants as an XCFramework, and wraps
  it in a local Swift Package. A clean package copy builds with a sanitized
  Swift-only environment, contains no repository path, installs and launches
  in Simulator, and writes `MOJO_IOS_PACKAGE_PASS` only after checking the
  exact Mojo greeting and sum. The final image contains one serial initializer.
- The same core-seed sources and emitted probes now compile and link as an
  artifact-only `IOS`/iOS 17 arm64 device executable with the `apple-a7`
  baseline. It performs no signing, installation, or physical-device launch.
- The canonical Bazel SwiftUI host links the Mojo archive and bounded serial
  core, installs and launches on the iPhone 17 Pro Simulator, and captures a
  1206x2622 screenshot whose visible text is `Hello from Mojo on iOS.` and
  `20 + 22 = 42`. The most recent run hash was
  `3ebe2137a813ce99f85c5466820422d1344c61bd22b1b30835df13a15d16e9d8`.
  XCTest and XCUITest independently assert those exact values; the screenshot
  remains visual evidence rather than OCR proof.
- A direct-C `os/signpost.h` fixture compiles and links both iOS slices,
  including the public signpost symbol and libSystem load, without launching
  or collecting signposts.
- KGEN and iOS-target tests pass.
- Device artifact preparation passes without signing or installation.

## Main blockers

1. N6–N9 are complete: the reviewed Apple dependency graph is direct, and
   the root custom C++ toolchain now has target-correct iPhoneOS and
   iPhoneSimulator sysroots, triples, libc++, compile/link policy, host tools,
   and Mach-O metadata. The always-on mypy aspect resolves its tool inputs in
   the macOS execution configuration during iOS cross-compilation. The Mojo and
   serial-core archives consume registered target toolchains in sandboxed,
   declared same-graph actions, and the canonical SwiftUI/XCTest/XCUITest app
   passes in Simulator. N10's XCFramework/local Swift Package clean consumer
   also passes without a Mojo installation. N11 now isolates and builds the
   smallest behavior-preserving serial iOS AsyncRT dependency graph.
   Historical controls showed why the earlier dependency versions were insufficient.
   A same-graph control advances past versionless `rules_mojo` and Jammy
   sysroots only with disposable local overrides, then stops because the
   consumed `modular` module cannot see its `@rules_mypy` development-dependency
   repository. A disposable protobuf-34 trial showed that the old development-
   dependency patch can be removed or ported for focused graph/KGEN checks, but
   the Apple transition still fails under Bazel 10. A newer disposable
   `rules_apple` 5.0.0-rc3 / `rules_swift` 4.0.0-rc5 control cleared that
   transition and identified the custom-toolchain work now completed by N7.
2. The full iOS-safe Mojo runtime is incomplete. Allocation, String lifetime,
   named-global teardown, a no-stack-trace Error construction path, and one
   sandboxed ordinary-file roundtrip now have target-correct Bazel archive and
   narrow Simulator evidence. Serial D6 work can continue without it, but
   N11 now compiles and archives the real AsyncRT CPU-device, AsyncValue,
   task/chain, timer, and serial work-queue graph for both iOS SDKs with malloc
   and no MLIR, LLVM Support, TCMalloc, JIT, signal, or plugin dependency. N12
   still must link the real public ABI and execute repeated
   `initialize_runtime()` plus task completion in Simulator; N13 owns the
   bounded mobile worker pool.
3. Physical-device signing, installation, and visible “Hello from Mojo” remain
   unverified.
4. Performance claims, Swift comparisons, broad Apple framework coverage, Core
   ML/ANE validation, Mojo-generated Metal kernels, CI, and upstream-quality
   packaging remain ahead.

## Estimated timeline

Assuming focused engineering time and no major compiler/runtime redesign:

- Root CcInfo provider and same-graph device/Simulator archive seam: complete.
- Root Apple rules, iOS C++ toolchain, N8 archive actions, N9 canonical Bazel
  app, N10 clean package consumption, and N11 AsyncRT graph isolation:
  complete; N12 runtime initialization correctness is next.
- Physical iPhone “Hello from Mojo”: approximately 1–3 days once a
  development-signed device is available.
- Usable static runtime plus allocation/String/error/core-stdlib subset:
  approximately 3–8 weeks; allocator/String, globals, and the no-stack-trace
  Error path are now bounded probes, while this remains the highest-risk phase.
- Initial device benchmarks and Swift comparison: approximately 2–4 weeks after
  runtime/device support.
- Broader framework adapters and Core ML packaging: approximately 1–3 months
  incrementally.
- Mojo-generated Metal on iOS: likely several additional months after iOS AIR
  lowering is implemented.
- Production-quality/upstreamable support: realistically 3–6+ months, with
  complete iOS/Swift framework coverage continuing as a staged effort.
